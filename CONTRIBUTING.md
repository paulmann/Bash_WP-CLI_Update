# Contributing

Patches, issues and failure stories are welcome. The bar is simple: the tool
runs as root against other people's websites at 3 a.m., so every change must
be **reviewable, testable and explainable**.

## Ground rules

1. **Edit `src/`, never the artifacts.** `Bash_WP-CLI_Update.sh` and
   `Find_WP_Senior.sh` are generated by `tools/build.sh`; `make check` fails a
   PR whose artifacts drifted from its sources.
2. `make check` (build + drift + shellcheck + the nine suites) must pass. The
   suites need no root, no WordPress, no WP-CLI and no network.
3. Bash **4.2** floor (CentOS/RHEL 7). That rules out: `declare -n` namerefs,
   `wait -n`, `mapfile -d`, `${var@Q}`, `$EPOCHSECONDS`. `printf '%(…)T'` and
   `printf -v` are fine.
4. GNU-coreutils assumptions are allowed (`stat -c`, `find -printf` avoided
   where a fallback exists) but every *optional* tool (flock, timeout, perl,
   jq, curl/wget, tar, gpg, logger) must degrade with a warning, never crash.
5. Comments explain **why**, especially where a naive rewrite would look
   cleaner. This codebase carries the scars of three prior revision lines; a
   comment like "do not simplify this into a string" is load-bearing.

## Adding a setting

One row in `CONFIG_SPEC` (`src/manager/01-bootstrap.sh`):
`KEY|TYPE|DEFAULT|one-line help`. That single row feeds the default, the
config-file whitelist, the environment layer, validation, `--print-config`,
`--init-config` and `docs/CONFIGURATION.md`. Then:

- add the flag in `parse_args` + `LONG_OPTIONS` (+ `config_flag_of` for
  messages); the pure-check suite fails if parser and option table disagree;
- mention it in `wp-cli-update.conf.example` and the README table when it is
  operator-facing;
- add a test: the config suite covers layering/validation generically, so
  usually one assertion on the new key's type is enough.

## Adding a mode

Three places, and the suite verifies all three exist:

1. a `MODE_TABLE` row (`name|short|readonly|description`) in
   `src/manager/16-cli.sh` — drives help, `--list-modes`, completion;
2. a `mode_<name>() { site user url … }` function in `12-modes.sh` (mutating)
   or `14-audit.sh` (read-only). Mutations go through `run_wp`, opportunistic
   steps through `run_wp_soft`, queries through `wp_data`/`wp_probe`/`info_wp`
   — never call `wp_exec` directly and never touch the counters by hand;
3. a branch in `dispatch_mode` (`17-fleet.sh`), plus an early-exit branch in
   `main` if the mode needs no fleet (like `--wpcli-*`).

If the mode contains mutating commands, extend `wp_is_readonly` — it is an
allowlist, so a *new* command is treated as mutating until you say otherwise.
That default is the point.

## Testing

```bash
bash tests/run_tests.sh              # everything
bash tests/run_tests.sh manager      # one suite
VERBOSE=1 bash tests/run_tests.sh    # keep fixtures for inspection
source tests/pure_check.sh           # fast inner loop: pure logic, <1s
```

The stub `wp` (`tests/stub/wp`) records its argv and obeys hooks:
`WP_FAIL_CMD='core update'`, `WP_HANG=6`, `WP_NOISY_JSON=1`,
`WP_MULTISITE=1`, `WP_CLI_NEWER=2.12.0`, `WP_CORE_UPDATE=6.5.3`,
`WP_BAD_CHECKSUMS=1`, `ASTRA_FAIL_SLUG=astra-addon`, `WP_STUB_VERSION_FILE`.
Assert on the recorded argv (`expect_grep_count "$ARGV_LOG" …`), not on log
wording, wherever both are possible: argv is the contract, wording is not.

## Style

- 4 spaces, `local` everything, `${1-}` for optional parameters under `set -u`.
- Arrays expand as `${arr[@]+"${arr[@]}"}` (bash 4.2 + `set -u` safe).
- No `set -e` in the products (a fleet tool handles errors by hand); `set -uo
  pipefail` stays.
- Hot-path helpers publish a global **and** may print; see the fork discipline
  in `docs/ARCHITECTURE.md` before adding a `$(…)` to a per-site path.
- Log messages are sentences an operator can act on at 3 a.m.: what happened,
  to which site, and what to do next.
- LF only (`.gitattributes` enforces); the static suite checks.

## Commit/PR hygiene

- One logical change per commit; the message says *why* (the diff says what).
- Touching security-relevant code (sections 6, 9, 12, 13 of the manager)?
  Read `docs/SECURITY.md` first and keep its guarantees true — the suites
  assert several of them (licence never in argv/logs, config never sourced,
  ids validated before delete).
- Run `tools/scan-secrets.sh --strict` before pushing; CI does.

## Releasing

1. `src/manager/01-bootstrap.sh` / `src/finder/01-bootstrap.sh`: bump
   `SCRIPT_VERSION` (+ `FINDER_VERSION` reference).
2. `CHANGELOG.md` entry; README version table; `docs/MIGRATION.md` when the
   contract moved.
3. `WPU_BUILD_ID=vX.Y.Z make build && make check`.
4. Commit sources **and** rebuilt artifacts together (the drift check binds
   them). Tag `vX.Y.Z`.
