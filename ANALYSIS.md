## 2. Критические дефекты (блокеры)

### 2.1. Инъекция команд / RCE от root — `main:376, 386–396, 468–475, 638, 812, 885`

Весь обмен с WP-CLI построен на сборке строки и передаче её в `su - user -c`:

```bash
# main:376
local wp_command="${WP_CLI_PATH} --path=\"${site_path}\" ${cmd[*]} --skip-plugins=... --quiet --allow-root"
# main:387
local full_command="cd \"${site_path}\" && ${export_vars} && ${wp_command}"
# main:396
output=$(su - "${user}" -c "${full_command}" 2>&1) || exit_code=$?
```

`${cmd[*]}` — это **неквотированная** склейка аргументов, куда попадают данные извне:

* имя плагина, полученное из `wp plugin list --format=json` (`manage_plugin_for_site`, `main:680, 715, 755/763/772`);
* путь сайта из `wp-found.txt` (файл может быть изменён кем угодно, кто имеет доступ на запись в каталог скрипта);
* значения `--site` / `--name` командной строки.

Скрипт обязан работать от root (`main:1445`), поэтому полезная нагрузка исполняется **от root**.

**PoC (воспроизведён).** В список плагинов подставлено имя:

```
evil; id -un > /tmp/wpmaint-pwned-legacy; #.php
```

Legacy-скрипт сформировал и выполнил:

```
su - "tihon" -c "cd "/tmp/poc/site" && export DOCUMENT_URI="site" && ... && /tmp/poc/bin/wp --path="/tmp/poc/site" \
   plugin deactivate evil; id -un > /tmp/wpmaint-pwned-legacy; #.php --skip-plugins=... --quiet --allow-root"
```

Результат: файл `/tmp/wpmaint-pwned-legacy` создан, содержимое — `root` в production-запуске (в PoC — непривилегированный пользователь, т.к. проверка root отключена).
Тот же вход в v6.0 приходит в WP-CLI **одним элементом argv**:

```
[mock wp] argc=6
  arg: <--path=/tmp/poc/site>
  arg: <plugin>
  arg: <deactivate>
  arg: <evil; id -un > /tmp/wpmaint-pwned-legacy; #>     ← данные, не код
```

Вектор атаки реалистичен: достаточно установленного/обновлённого плагина, в заголовке которого есть метасимволы (`Plugin Name:` в PHP-файле), либо прав на запись в `wp-found.txt`.

**Исправление в v6.0:** единственный путь запуска — `run_wp()` c массивом `WP_CMD=(wp --path=… --no-color …)`, обёртка `runuser -u user -- env HOME=… <массив>`; для fallback-режима `su` аргументы сериализуются через `printf '%q'` (`shell_join`). Ни одна строка не собирается интерполяцией.

### 2.2. `Find_WP_Senior.sh --output FILE` — гарантированное падение без диагностики (finder:377)

```bash
[[ -z "${OUTPUT_FILE:-}" ]] && OUTPUT_FILE="${DEFAULT_OUTPUT_FILE}"   # finder:377
```

Это последняя команда `parse_args()`. Если `--output` передан, условие ложно → функция возвращает 1 → вызов `parse_args "$@"` стоит не в условии → `set -e` завершает скрипт.

Проверено на bash 3.2 и 5.2:
```
$ bash Find_WP_Senior.sh --output /tmp/out1.txt ./root
INFO: WordPress discovery started...
INFO: Cleaned up temporary files.
exit=1                      ← файл не создан, сайты не найдены, причина не сообщена
```

**Исправление:** в v2.0 значения по умолчанию применяются отдельно от разбора аргументов, ни одна функция не заканчивается «висящим» `&&`-списком, `--output` поддержан и в форме `--output=FILE`.

### 2.3. Молчаливая потеря сайтов из-за масок исключений (finder:87–101, 225)

```bash
'*/.git' '*/node_modules' '*/vendor' '*/backup*' '*/old*' '*/test*' '*/tests*'   # finder:96-100
...
if [[ "${site_dir}" == ${exclude} ]]; then continue 2; fi                         # finder:225
```

Маска применяется к **полному пути** сайта, поэтому под неё попадают легитимные сайты:

* `/var/www/test.example.com`, `/var/www/tests`, `/var/www/test-club.ru` → `*/test*`;
* `/var/www/oldboy.com`, `/var/www/gold-site.ru` (!) → `*/old*`;
* `/var/www/backup-host.ru` → `*/backup*`.

Сайт не попадает в `wp-found.txt` → он **никогда не обслуживается**, при этом никаких предупреждений нет. Это худший класс дефекта для maintenance-инструмента: тихая потеря покрытия.

**Исправление:** в v2.0 исключения разделены на *имена* (`.git`, `node_modules`, `vendor`, `cache`, `backups`…) и *пути* (если шаблон содержит `/`), применяются через `-name`/`-path` в `find`, а опасные `test*`/`old*` из дефолтов убраны. Ложных срабатываний на `test.example.com`/`oldboy.com` больше нет (проверено тестом).

### 2.4. Абсолютные исключения в finder не работают, выражение собирается строкой (finder:137–148, 209)

```bash
build_prune_args() { ... printf '%s ' "${prune_args[@]}"; printf '%s' '-print'; }   # возвращает СТРОКУ
...
find "${root}" -maxdepth "${MAX_DEPTH}" \( -type d \( -name '.no_wp_cli' ... \) -prune \) -o \
     \( -type f -name "wp-config.php" ${prune_expr} \) 2>/dev/null                   # неквотированная подстановка
```

Что не так:

1. `${prune_expr}` разворачивается без кавычек → word splitting + globbing (shellcheck SC2086); путь с пробелом или `*` ломает выражение.
2. `-path P -prune` применяется к **файлу** `wp-config.php`, а не к каталогу: `-prune` для файла бессмысленен, подкаталоги исключённого пути всё равно сканируются, а совпадение возможно только при точном равенстве пути.
3. Исключения для несуществующих каталогов молча игнорируются (`[[ -d "${path}" ]]`).
4. `-name '.no_wp_cli'` для `-type d` не срабатывает: маркер — это файл (работает только пост-проверка).

**Исправление:** выражение `find` строится **массивом** (`FIND_EXPR`), каталоги отсекаются через `-type d \( -path … -o -name … \) -prune`, вывод NUL-разделённый (`-print0` + `read -d ''`), ошибки `find` больше не роняют скрипт (код возврата перехватывается и логируется).

### 2.5. `su -` (login shell) — падение на `www-data` и мусор в JSON (main:396, 475, 491, 638, 812, 885)

* `su - user -c` запускает **login shell**, который читает `/etc/profile` и `~/.bash_profile` пользователя сайта. Любой `echo`/`wp`-хук оттуда попадает в stdout, который скрипт затем парсит как JSON (отсюда и «костыль» `clean_json_output`).
* На Debian/Ubuntu у `www-data` shell = `/usr/sbin/nologin`: `su - www-data -c …` завершается ошибкой «This account is currently not available», т.е. на типовом хостинге скрипт не работает вообще.
* `cd "${site_path}"` не нужен: WP-CLI полностью определяется `--path`.

**Исправление:** приоритет `runuser -u user --` (util-linux, без shell и без профилей) → `sudo -n -u user --` → `su -s /bin/sh user -c` (с `%q`-экранированием). Дополнительно введён режим `--no-user-switch` для запуска от текущего пользователя (Docker, cron от имени владельца сайта).

### 2.6. Утечка лицензионного ключа Astra (main:109–116, 373, 825, 892, 894)

* `log_error_detail` пишет в `wp_cli_errors.log` **полную команду**, включая `brainstormforce license activate astra-addon "$ASTRA_KEY"`;
* `log_info "Running: wp ${cmd[*]} …"` (main:373) дублирует её в `wp_cli_manager.log`;
* `debug_echo "🔑 Activating license with key: ${ASTRA_KEY}"` (main:892) печатает ключ в консоль;
* ключ передаётся аргументом → виден в `ps` любому пользователю системы.

**Исправление:** `ASTRA_KEY_FILE` (root-owned, 0600) как основной способ, `redact()` применяется в логировании и в блоке ошибок, ключ никогда не печатается. Остаточное ограничение (аргумент командной строки для `brainstormforce license activate`) задокументировано: сторонняя команда не умеет читать ключ из stdin.

## 3. Серьёзные дефекты основного скрипта

### 3.1. Статистика ошибок врёт: exit code 1 при полностью успешной работе (main:799, 863)

```bash
if ! run_wp_cli "${site_path}" "${wp_user}" plugin status astra-addon >/dev/null 2>&1; then
    log_warning "Astra plugin not found or not active"; return 0
fi
```

`run_wp_cli` **всегда** меняет счётчики (`main:359, 408, 418`), в том числе для проверок. Значит, на каждом сайте без установленного Astra Pro `error_ops` растёт, а в конце:

```bash
if [[ ${STATS[error_ops]} -eq 0 ]]; then exit 0; else exit 1; fi      # main:1563-1568
```

→ скрипт возвращает 1, cron/CI считает ночной прогон аварийным. В режиме `--astra` ошибка учитывается ещё и дважды (`main:866` + `process_site`).

**Исправление:** разделены три вида вызовов — `run_wp` (учитывается), `wp_probe` (проверка, без статистики), `wp_soft` (необязательный шаг: только предупреждение). Astra определяется через `plugin list`, а не через «probe с побочным эффектом».

### 3.2. Обработка ошибок и коды возврата сломаны (main:1012, 1015, 1489, 1519)

* `process_site()` **всегда** возвращает 0 (`return 0` в конце, main:1015), поэтому `if ! process_site …` (main:1519) никогда не срабатывает;
* результат `execute_mode` (main:1012) игнорируется;
* при этом в режиме `--site` вызов идёт **не** в условии, а `set -e` активен: первая же неудачная WP-команда убивает скрипт целиком (в отличие от мультисайтового режима, где `set -e` подавлен контекстом условия). Поведение зависит от режима запуска;
* `main:1032–1044` — ни одна команда не проверяется: падение `plugin update --all` не мешает отчитаться об успехе (кроме счётчика).

**Исправление:** каждый шаг явно обрабатывается (`|| rc=1`), `process_site` возвращает реальный статус, введены коды возврата 0/1/2/3/4/130 и пер-сайтовый отчёт `Results:`.

### 3.3. `--skip-plugins` не делает того, что обещает README (main:376, 469, 812; README:207)

`--skip-plugins=...` — глобальный флаг WP-CLI, он лишь **не загружает** перечисленные плагины в bootstrap. `wp plugin update --all` всё равно обновит их. README же утверждает «Skips problematic plugins during updates».
**Исправление:** для исключения из обновления добавлен `--exclude-plugins LIST` (→ `plugin update --all --exclude=…`), а `--skip-plugins` оставлен как «bootstrap safety» с честной документацией.

### 3.4. `get_plugins_json`: параметр игнорируется, ошибки «залипают» (main:462, 504–506, 557–560)

* функция объявлена как `get_plugins_json() { local site_path="$1" wp_user="$2"; …}`, но вызывается с третьим аргументом `true`/`false` (main:557, 560, 669), который должен управлять подавлением stderr. Аргумент **не читается** → «повтор без подавления» не происходит, ветка `if [[ "${DEBUG_MODE}" == true ]]` (main:487) вообще недостижима в обычном режиме.
* `LAST_WP_CLI_ERROR` заполняется только при ошибке и **никогда не сбрасывается** → на следующем сайте в диагностике фигурирует ошибка предыдущего (`main:561, 670`).

**Исправление:** единый `load_plugins()`, который возвращает реальный код возврата; ошибки не «залипают», а сразу попадают в лог/консоль с контекстом сайта.

### 3.5. jq-инъекция в фильтрах (main:573, 680, 721)

```bash
plugins_json=$(echo "${plugins_json}" | jq -c "[.[] | select(.name | test(\"${plugin_filter}\"; \"i\"))]")
current_status=$(echo "${plugins_json}" | jq -r ".[] | select(.name == \"${exact_plugin_name}\") | .status")
```

Пользовательское `--name` и имя плагина из JSON подставляются в **текст jq-программы**. Кавычка/обратный слэш ломают программу (в лучшем случае — ошибка парсинга, в худшем — неверная выборка). Это не RCE, но корректность и предсказуемость теряются.
**Исправление:** в v6.0 jq используется только для преобразования *вывода* (`@tsv`), фильтрация выполняется в bash без интерполяции; при отсутствии jq работает CSV-ветка (свой парсер с поддержкой кавычек и запятых внутри полей — проверено тестом `WooCommerce, Inc.`).

### 3.6. Поле `slug` не существует → колонка всегда «N/A» (main:599, 614, 632)

В `wp plugin list` нет поля `slug` (сверено с документацией команды); `jq -r '.slug // "N/A"'` всегда даёт `N/A`.
**Исправление:** slug вычисляется из имени файла (`akismet.php` → `akismet`).

### 3.7. `grep -c … || echo 0` → арифметическая ошибка и падение под `set -e` (main:640, 702)

```bash
count=$(echo "${table_out}" | grep -c "^|" || echo 0)      # при 0 совпадений: "0\n0"
count=$((count > 2 ? count - 2 : 0))                       # bash: 0\n0: syntax error in expression
```

Проверено: `bash: 0 0: syntax error in expression`, код возврата 1 → под `set -e` скрипт завершается. Ветка достижима на любой системе без `jq` при пустом списке плагинов.
**Исправление:** подсчёт в bash, без `grep -c || echo`.

### 3.8. Конфликт stdin: подтверждение удаления «съедает» список сайтов (main:737, 1506, 1523)

Цикл по сайтам читает файл через `done < "${SITES_FILE}"` (main:1523), а `read -r -p "Type 'DELETE'…"` (main:737) читает **тот же** stdin → в ответ на подтверждение приходит путь следующего сайта, условие `!= DELETE` всегда истинно → удаление никогда не выполняется, а один сайт молча пропускается. Дочерние `su`/`wp` также наследуют stdin.
**Исправление:** список читается один раз в массив (`mapfile`-подобный цикл), подтверждение читается только из `/dev/tty`, для всех WP-вызовов stdin = `/dev/null`, при отсутствии TTY требуется `--yes`.

### 3.9. `ensure_sites_file` (main:927–982)

* `read -r -p` без проверки TTY → в cron получает EOF → «No path provided» → `exit 1`;
* при отсутствии файла запускается `"${DISCOVER_SCRIPT}"` **без `--output`**, а finder по умолчанию пишет в `${PWD}` (finder:70), тогда как main читает `${SCRIPT_DIR}/wp-found.txt` (main:26) → рассинхрон каталогов;
* пустой существующий файл считается нормой: 0 сайтов, «Maintenance completed», exit 0.

**Исправление:** обнаружение вызывается с явным `--output "${SITES_FILE}"`, ввод только при TTY, пустой список → отдельный код возврата 4 и понятное сообщение.

### 3.10. Выдуманное окружение для WP-CLI (main:378–386, 468)

```bash
home_dir="$(dirname "$(dirname "${site_path}")")"     # для /var/www/site.com → /var
DOCUMENT_URI="${domain}"                              # DOCUMENT_URI — это URI, а не имя каталога
HTTP_HOST="${domain}"                                 # для /var/www/site.com/public_html → "public_html"
```

Значения бессмысленны и подмешиваются в окружение WP-CLI: `HOMEDIR=/var` (должен быть домашний каталог пользователя), `HTTP_HOST=public_html` влияет на генерацию ссылок плагинами. Для мультисайта правильный механизм — `--url`.
**Исправление:** переменные не подменяются; `HOME` берётся из passwd целевого пользователя; `--url` определяется из `WP_HOME`/`WP_SITEURL` в `wp-config.php` или задаётся `--url` (для мультисайта — с предупреждением).

### 3.11. Определение пользователя сайта (main:252–340)

* метод 3 (`path_parts[3]`, main:307) для `/var/www/html` даёт `html`, для `/home/user/…` — `public_html`; при совпадении с существующим пользователем будет выбран **неверный** пользователь;
* метод 4 — `DB_USER` из `wp-config.php` (main:325): пользователь БД не является системным пользователем, это ложная эвристика, приводящая к работе WP-CLI «не тем» пользователем и порче прав на файлы;
* `root` как владелец отбрасывается всегда (main:266) — для сайтов, действительно работающих от root, детект провалится;
* нет способа задать пользователя вручную (ни флага, ни per-site файла).

**Исправление:** порядок `--user` → `DEFAULT_USER` → `<site>/.wp-cli-user` → владелец `wp-config.php` → владелец корня → владелец `wp-content`; `DB_USER` и «угадывание по пути» удалены; имя пользователя валидируется регуляркой; root отклоняется с понятным сообщением (обход — `--force`).

### 3.12. Логи

* `echo "=== … ===" > "${ERROR_LOG_FILE}"` (main:1281) — **обрезает** историю ошибок при каждом запуске; при параллельных запусках логи затирают друг друга;
* нет ротации: `wp_cli_manager.log` растёт неограниченно (`>>`, main:93);
* нет проверки каталога/прав; запись без обработки ошибок (под `set -e` падение в середине прогона);
* `log()` использует `echo -e` (main:95–100), а `print_wp_error` вставляет вывод WP-CLI в `echo -e` (main:434–443) → `\c`, `\n`, `\033` из вывода плагинов интерпретируются и искажают лог (лог-инъекция);
* в лог попадают секреты (см. 2.6).

**Исправление:** `printf '%s'` вместо `echo -e`, append + маркер запуска (`RUN_ID`), ротация по размеру, конфигурируемый `--log-dir`, редактирование секретов, устойчивость к недоступному каталогу.

### 3.13. Прогресс-бар: мусор в C-локали и «не прогресс» (main:138–166)

```bash
printf '%*s' "${filled}" '' | tr ' ' "${PROGRESS_CHAR}"     # PROGRESS_CHAR="█"
```

GNU `tr` работает побайтово: в локали C/`POSIX` пробел заменяется первым байтом UTF-8 (`0xE2`) — проверено, вывод `342 342 342`. Кроме того, `printf … "\n"` (main:158) печатает новую строку на каждый сайт, т.е. это не прогресс-бар, а «ёлочка»; `finalize_progress` (main:164) не вызывается нигде (shellcheck SC2317).
**Исправление:** заполнение через `printf -v` + `${var// /─}`, прогресс одной строкой с `\r`, вывод только при TTY.

### 3.14. Дубли и мёртвый код

* блок «стартовый баннер» продублирован (main:1458–1462 и 1464–1469);
* итоговый отчёт печатается **дважды** — простой `echo`-блок (main:1534–1539) и рамка (main:1549–1560);
* `_handle_astra_operations` содержит недостижимый хвост после `return` (main:921 — SC2317);
* `log_debug` (main:123–127) и `finalize_progress` (main:164) не используются;
* `usage()` возвращает 1 даже для `--help` (main:205) — «справка по запросу» выглядит как ошибка для CI.

**Исправление:** единственный баннер, единственный отчёт, `--help` → 0, неиспользуемый код удалён.

### 3.15. Прочее по main

* нет поддержки `--opt=value` (кроме нового `--sites-file`), `--site --foo` отклоняется по префиксу `--`, конфликт режимов (`--full --plugins`) разрешается «последний победил» — теперь это ошибка;
* нет блокировки от одновременных запусков; нет `trap` на INT/TERM (Ctrl-C посреди `core update` → нет отчёта и «висящий» lock-файл в будущем);
* нет таймаутов: зависший `wp` (сетевой запрос к api.wordpress.org) блокирует прогон навсегда;
* нет `--dry-run`, нет бэкапа перед обновлением, нет `--only-active`, нет параллелизма, нет `--status`/`--verify`;
* `readonly SCRIPT_DIR="$(cd … && pwd)"` (main:17) не разворачивает симлинки: запуск через `/usr/local/bin/wp-update` → логи и `wp-found.txt` уезжают в каталог симлинка;
* `log "ERROR"` без второго аргумента падал бы с unbound variable (нет значения по умолчанию).

## 5. Что проверено и дефектом НЕ является

Чтобы не выдавать догадки за факты:

* `wp db optimize` / `wp db repair` / `wp db size` — команды существуют (проверено по документации WP-CLI).
* `--quiet` **не** подавляет вывод `wp plugin list --format=json`: в WP-CLI 2.x `WP_CLI::line()` намеренно игнорирует `--quiet`, а форматтер выводит через `line()` (проверено по `php/class-wp-cli.php` v2.11 и `php/WP_CLI/Formatter.php:317`). То есть `get_plugins_json` ломается не из-за `--quiet`; тем не менее в v6.0 для машинного вывода `--quiet` не передаётся.
* `$HEADER_SHOWN && return 0` (main:1103) при `HEADER_SHOWN=false` **не** роняет скрипт (проверено): сбой левой части `&&`-списка не считается срабатыванием `set -e`. Это плохой стиль (SC2091), но не баг.
* EXIT-trap не «съедает» код возврата: `trap "false" EXIT; exit 3` → 3 (проверено на bash 5.2).
* `wp plugin update --all` не требует `--yes` при неинтерактивном stdin.
* Дублирование `show_startup_info` (main:1458–1469) не приводит к двойному выводу из-за флага `HEADER_SHOWN` — это мёртвый код, а не двойной баннер (в отличие от двойного **summary**, см. 3.14).

## 6. Что сделано в v6.0.0 / v2.0.0

### 6.1. Безопасность

* запуск WP-CLI только через массив аргументов; `runuser`/`sudo`/`su` c `printf '%q'`;
* stdin всех WP-вызовов — `/dev/null`; подтверждения — только `/dev/tty`;
* конфиг-файл не выполняется, если он group/world-writable, и предварительно проверяется `bash -n`;
* имена пользователей валидируются, `eval` в `user_home` отсутствует (был бы ещё один вектор через `.wp-cli-user`);
* секреты не попадают в логи (`redact`), ключ можно держать в файле 0600;
* `--no-user-switch` явно фиксирует модель привилегий; root отклоняется как пользователь сайта без `--force`.

### 6.2. Надёжность

* три уровня вызовов: `run_wp` (учитывается в статистике), `wp_probe` (только чтение), `wp_soft` (необязательный шаг);
* явная обработка кодов возврата, пер-сайтовый отчёт, коды 0/1/2/3/4/130 (см. таблицу ниже);
* блокировка от параллельных запусков (`mkdir`-lock с проверкой живости pid), `trap` на INT/TERM с отчётом;
* ротация логов, маркер запуска в error-log, устойчивость к недоступному каталогу логов;
* таймауты на команды (`timeout`, по умолчанию 600 с; для `db export` таймаут снимается);
* `--dry-run`: read-only команды выполняются, `core/plugin/theme update` — с `--dry-run`, изменения (`db optimize`, `cron`, `plugin delete`) — пропускаются с логом;
* `--jobs N` — пакетный параллелизм с изоляцией stderr на сайт, буферизацией вывода и честной агрегацией статистики;
* бэкапы: `wp db export` (`--backup db|full`) и `tar` каталога плагина перед удалением, ретенция `--keep-backups`, каталог создаётся с владельцем-пользователем сайта (`install -d -o …`).

### 6.3. Функциональность

* режимы прежние + новые `--status` (версия ядра, URL, число обновлений, размер БД) и `--verify` (checksums ядра и плагинов);
* `--only-active` — обновление только активных плагинов, у которых есть обновление (список формируется явно: `plugin update <slug>…`);
* `--exclude-plugins` — честное исключение из `plugin update --all`;
* `plugin-manage`: точное совпадение slug выигрывает у частичного (в v5 `-N jetpack` при наличии Jetpack Boost отказывался работать), «уже активно/неактивно» = не ошибка, удаление с автодеактивацией и бэкапом;
* инвентаризация плагинов: таблица с реальными ширинами (без обрезки имён), корректная колонка slug, `--json` (JSON Lines: объект на сайт + итоговый объект);
* `--sites-file`, `--list-sites`, `--config`, `--user`, `--url`, `--log-dir`, `--backup-dir`, `--wp-bin`, `--timeout`, `--quiet/--verbose/--debug`, `--no-color`, `--strict`;
* конфиг-файл с приоритетом «CLI > окружение > файл > дефолты» (правило `: "${VAR:=default}"` внутри файла).

### 6.4. Finder v2.0.0

* рабочий `--output FILE` / `--output -` (и `--output=FILE`), атомарная замена через `mktemp` + `mv`, понятные ошибки при отсутствии/недоступности каталога;
* исключения: `-name` для имён, `-path` для шаблонов с `/`, отсечение **поддеревьев**; опасные `test*`/`old*` убраны; проверено, что `test.example.com` и `oldboy.com` находятся;
* NUL-safe обход (`-print0`), локальные счётчики (без подshell), ошибки `find` логируются и не роняют скрипт;
* корректное определение корня WP: поддержка «wp-config.php на уровень выше ядра» и Bedrock (`wp/`, `web/wp`, `htdocs`, `public`, `core`, `wordpress`);
* `--max-depth N`, `--follow` (симлинки + дедупликация по каноническому пути), `--json`, `--quiet`, `--verbose`, `--dry-run`, `--fail-if-empty` (exit 3), `--no-color`, `--version`;
* `DEFAULT_OUTPUT_FILE` = `<каталог скрипта>/wp-found.txt` (совпадает с main), но переопределяется `-o`;
* таблица с владельцем/группой/датой (портативный `stat` для GNU и BSD), вывод диагностики в stderr, машинные данные — в stdout;
* проверка версии bash с внятным сообщением вместо `declare: -A: invalid option`.

## 8. Совместимость и изменения поведения

Сохранено: имена и расположение файлов по умолчанию (`wp-found.txt`, `wp_cli_manager.log`, `wp_cli_errors.log`), все прежние режимы и короткие флаги (`-f -c -p -t -d -x -r -s -l -m -D -S -A -N -F -J -h`), формат `wp-found.txt` (пути, `#` — комментарий), дефолтный список `--skip-plugins` из v5.

Осознанные изменения (нужно знать при миграции):

1. `Find_WP_Senior.sh` по умолчанию пишет `wp-found.txt` **рядом со скриптом**, а не в `$PWD`; при вызове из main путь передаётся явно (`--output`).
2. Таблица найденных сайтов у finder печатается, только если stderr — терминал (или явный `-d`); при `--quiet` — не печатается.
3. `--help` возвращает 0 (было 1).
4. Бэкап по умолчанию **выключен** (как в v5); включается `--backup db|full`. Исключение — удаление плагина: tar-архив каталога плагина создаётся всегда, отключается `--no-backup`.
5. Список `--skip-plugins` больше не влияет на состав обновляемых плагинов — для этого `--exclude-plugins`.
6. Ошибка в одной WP-команде больше не обрывает прогон в режиме `--site` (раньше `set -e` убивал скрипт), но и не «прячется»: сайт помечается FAIL, итоговый код 1.
7. Пустой список сайтов → код 4 (было 0).
8. Требуется Bash 4.2+ с внятной проверкой (в v5 при bash 3.2 падало с `declare: -A: invalid option`).
9. Файлы скриптов теперь исполняемые (`chmod +x`) и имеют корректный shebang `#!/usr/bin/env bash` у обоих.

## 10. Остаточные ограничения

* Ключ Astra по-прежнему передаётся аргументом сторонней команде `brainstormforce license activate` (ограничение плагина): он виден в `ps` в момент вызова. Митигация — короткое окно, файл ключа 0600, редактирование во всех логах.
* `--jobs N` реализован пакетами (барьер на батч), а не непрерывным пулом: это осознанный компромисс для Bash 4.2 (нет `wait -n`).
* В параллельном режиме вывод сайтов буферизуется и печатается пакетом после его завершения (чтобы не смешивать строки разных сайтов).
* Парсер CSV (fallback без `jq`) в не-UTF-8 локали может искажать многобайтные *заголовки* плагинов (имена/slug — ASCII). Рекомендуется `jq` (используется автоматически, если найден).
* Ширина таблицы плагинов считается в байтах: для CJK-заголовков выравнивание будет неточным.
* `wp cron event run --due-now` и `wp db optimize` выполняются без проверки «есть ли что делать» — как в v5.
